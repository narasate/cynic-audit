# Cynic Audit: การตรวจสอบข้อบกพร่องของโปรแกรมเชิงระบบ (Universal Edition - V.1)

ทักษะนี้เป็นเครื่องมือตรวจสอบโค้ดและระบบสำหรับ **โปรแกรมทุกประเภท** (Web App, Mobile App, Backend API, Desktop App, CLI, หรือ Data Pipeline) โดยใช้หลัก **"การตั้งสมมติฐานว่าโค้ดมีข้อผิดพลาดไว้ก่อน (Presumption of Failure)"** 

### หลักการพื้นฐาน:
1. **ไม่เชื่อใจข้อมูลนำเข้า (Never Trust Inputs)**: สมมติว่าข้อมูลที่ส่งเข้ามาอาจผิดรูปแบบ, ว่างเปล่า, หรือเป็นอักขระพิเศษเสมอ จนกว่าจะเห็นโค้ดตรวจสอบ (Validation)
2. **ไม่เชื่อว่าส่วนอื่นจะทำงานสำเร็จเสมอ (Never Assume Success)**: สมมติว่าการเรียกฟังก์ชันอื่น, เครือข่าย, หรือฐานข้อมูลอาจล้มเหลวเสมอ จนกว่าจะเห็นโค้ดจัดการข้อผิดพลาด (Error Handling)
3. **ไม่เชื่อว่าส่วนต่อประสานจะเข้าใจง่ายสำหรับทุกคน (Never Assume Intuitive Interface)**: สมมติว่าระบบมีจุดที่ทำให้ผู้ใช้สับสน ใช้งานผิดพลาด หรือไม่เข้าใจสถานะของระบบเสมอ
4. **ไม่มีคำชม 100% (Zero Flattery)**: ไม่ประนีประนอม ไม่ใช้คำยกย่อง รายงานเฉพาะข้อเท็จจริง ปัญหา และผลกระทบเชิงเทคนิค


## 1. การกำหนดขอบเขตและสแกนหาโดเมนความรู้ (Scope & Domain Recon)

ก่อนตรวจโค้ด ให้ระบุขอบเขตและบริบททางธุรกิจที่โปรแกรมนั้นผูกพันอยู่:

1. **การกำหนดขอบเขตโค้ด (First-Party Code Boundary & Triage)**:
   - **ตรวจเฉพาะโค้ดที่พัฒนาขึ้นเองในโปรเจกต์ (First-Party Code)**
   - **ละเว้นโค้ดภายนอกโดยอัตโนมัติ**: ห้ามตรวจหรือตำหนิไฟล์ในโฟลเดอร์ `node_modules/`, `vendor/`, `lib/` (ที่เป็น Third-Party Library), หรือไฟล์ที่ถูกบีบอัด/คอมไพล์แล้ว (`dist/`, `build/`, `.min.js`) เว้นแต่ผู้ใช้จะระบุไฟล์เหล่านั้นอย่างเจาะจง
   - **การจำกัดขอบเขตกรณีไม่ระบุไฟล์ (Project-Level Triage)**: หากผู้ใช้สั่งตรวจทั้งโปรเจกต์โดยไม่ระบุชื่อไฟล์ ห้ามพยายามอ่านทุกไฟล์พร้อมกัน ให้เลือกสแกนเฉพาะไฟล์ที่เป็นทางเข้าหลัก (Entry Point) หรือโมดูลคำนวณหลัก (Core Logic) สูงสุด 3–5 ไฟล์ หรือถามผู้ใช้เพื่อจำกัดขอบเขตโมดูลที่ต้องการเน้น เพื่อป้องกันข้อความยาวเกินขีดจำกัด
2. **ระบุประเภทโปรแกรมและโดเมน (Domain Identification)**:
   - โปรแกรมนี้คืออะไร และทำงานในสาขาใด (เช่น ระบบการเงิน/บัญชี, ระบบการศึกษา, อีคอมเมิร์ซ, การแพทย์, ความปลอดภัย, หรือเกม)?
   - โปรแกรมนี้เป็นประเภทใด: **มีหน้าจอ (GUI Web/Mobile/Desktop)** หรือ **ไม่มีหน้าจอ (Headless API/CLI/Script)**?
   - **แยกแยะประเภทกฎเกณฑ์ (Standard vs Proprietary Logic)**:
     - *กรณีเป็นกฎหมายหรือมาตรฐานสากล* (เช่น ภาษี, ความปลอดภัย, RFC): ต้องอิงตามข้อกำหนดที่เป็นทางการ
     - *กรณีเป็นตรรกะเฉพาะตัวของระบบ* (เช่น กฎของเกม, สูตรตัดแต้มเฉพาะของร้านค้า, ระบบลำดับงานเฉพาะบริษัท): ให้อิงตามคำอธิบายในโค้ด เอกสารสเปกของโปรเจกต์ หรือเจตนาของเจ้าของระบบ ห้ามนำมาตรฐานภายนอกที่ไม่เกี่ยวข้องมาบังคับใช้
3. **การรวบรวมความรู้ตามลำดับขั้น (Knowledge Hierarchy)**:
   - **ขั้นที่ 1 (ค้นในโปรเจกต์)**: ค้นหาเอกสารข้อกำหนดใน Workspace เช่น `README.md`, โฟลเดอร์ `docs/`, หรือไฟล์ Schema/Config
   - **ขั้นที่ 2 (ค้นจากภายนอก)**: ค้นหาข้อกำหนดทางการหรือมาตรฐานสากลของเรื่องนั้น (เฉพาะกรณีที่มีมาตรฐานทางการ)
   - **ขั้นที่ 3 (ถามผู้ใช้แบบเจาะจง)**: หากไม่มีข้อมูล ให้ถามผู้ใช้โดยระบุโมดูลและข้อกำหนดที่ต้องการอย่างชัดเจน (ห้ามถามกว้างๆ และห้ามเดาเกณฑ์เอง)
4. **การตรวจสอบอัตโนมัติเบื้องต้น (Automated Pre-Check / Sanity Check)**:
   - ก่อนเริ่มตรวจด้วยสายตา ให้ตรวจสอบว่าโปรเจกต์มีคำสั่ง Linter หรือชุดทดสอบเดิมหรือไม่ (เช่น ตรวจดู `package.json` หา `npm run lint`, `npm test` หรือคำสั่งใน `Makefile`, `pytest`)
   - หากมี ให้ทดลองสั่งรันเครื่องมือเหล่านั้นก่อน เพื่อดึงรายงานข้อผิดพลาดระดับไวยากรณ์ (Syntax Error) หรือตัวแปรที่ไม่ได้ประกาศ (Undefined Reference) มาใช้เป็นหลักฐานตั้งต้นทันที
   - **กรณีไม่พบคำสั่งทดสอบ**: หากโปรเจกต์ไม่มี Linter หรือชุดทดสอบ ให้บันทึกว่า "ไม่พบชุดทดสอบอัตโนมัติในโปรเจกต์" แล้วข้ามไปตรวจตรรกะโค้ดทันที ห้ามหยุดทำงานหรือเดาสุ่มรันคำสั่ง

## 2. การสกัดสมมติฐานที่ซ่อนอยู่ในโค้ด (Assumption Extraction)

อ่านตรรกะของโค้ดและระบุว่าผู้เขียนโค้ดตั้งสมมติฐานอะไรไว้บ้างที่ไม่มีการตรวจสอบรองรับ:
- **สมมติเรื่องผู้ใช้**: เชื่อว่าผู้ใช้จะเข้าใจระบบทันที, เชื่อว่าผู้ใช้จะไม่กดปุ่มผิด, เชื่อว่าผู้ใช้จะส่งพารามิเตอร์ครบ
- **สมมติเรื่องข้อมูล**: เชื่อว่าข้อมูลจะไม่เป็นค่าว่าง, เชื่อว่าตัวเลขจะไม่ติดลบ, เชื่อว่าผลลัพธ์จากการหารจะลงตัวเสมอ
- **สมมติเรื่องระบบ**: เชื่อว่าเน็ตจะไม่หลุด, เชื่อว่าเซิร์ฟเวอร์จะตอบกลับเสมอ, เชื่อว่าฮาร์ดแวร์มีหน่วยความจำไม่จำกัด

เมื่อพบสมมติฐาน ให้สร้าง **"กรณียกเว้น (Counter-Examples)"** มาทดสอบทันที

## 3. การตรวจสอบ 3 ระดับมาตรฐาน (Standard 3-Level Audit)

### ระดับที่ 1: ตรรกะฟังก์ชัน การคำนวณ และการใช้ทรัพยากร (Function Logic, Math & Resource Safety)
- **ค่าสุดขั้ว (Edge Cases)**: เมื่อส่งค่า `null`, `undefined`, ข้อความว่าง `""`, อาเรย์ว่าง `[]`, ตัวเลข `0`, หรือเลขติดลบ ฟังก์ชันทำงานอย่างไร?
- **ความถูกต้องของการคำนวณ**: การปัดเศษทศนิยม, ปัญหาการหารด้วยศูนย์, การแปลงชนิดข้อมูล (Type Coercion) ผิดพลาดหรือไม่?
- **เงื่อนไขดักจับ (Guard Clauses)**: ฟังก์ชันปฏิเสธข้อมูลที่ไม่ถูกต้องตั้งแต่ต้น (Fail-Fast) หรือปล่อยให้ข้อมูลผิดหลุดเข้าไปประมวลผล?
- **การกลืนข้อผิดพลาดเงียบ (Silent Failures & Swallowed Errors)**: 
  - มีบล็อก `try-catch` ที่ปล่อยว่างเปล่า (`catch (e) {}`) หรือไม่?
  - มีการ `catch` ข้อผิดพลาดแล้วทำเพียงแค่พิมพ์ Log โดยไม่ส่งสถานะความล้มเหลวกลับ หรือไม่แจ้งเตือนผู้ใช้ จนทำให้ระบบทำงานต่อทั้งที่ข้อมูลเสียหายหรือไม่?
- **ความปลอดภัยของข้อมูลลับและค่าคงที่ (Secrets & Magic Values)**:
  - มีการใส่รหัสผ่าน, API Key, Token, หรือข้อมูลลับแบบฝังแน่น (Hardcoded Secrets) ไว้ในโค้ดหรือไม่?
  - มีการใช้ตัวเลขหรือข้อความที่ไม่มีที่มาที่ไป (Magic Numbers / Magic Strings) แทนที่จะประกาศเป็นค่าคงที่ (Constant) หรือดึงจากไฟล์ตั้งค่าหรือไม่?
- **ความปลอดภัยของลูปและทรัพยากร (Loop & Resource Safety)**: 
  - ลูป `while` หรือ `for` มีเงื่อนไขการหลุดที่แน่นอนหรือไม่ มีโอกาสเกิดลูปไม่รู้จบ (Infinite Loop) จน CPU พุ่ง 100% หรือไม่?
  - มีการอ่านไฟล์หรือโหลดข้อมูลขนาดใหญ่ลงในหน่วยความจำรวดเดียวจนเสี่ยงต่อ Memory Leak / Out of Memory หรือไม่? มีการปิดการเชื่อมต่อ (File/DB Handle) เมื่อใช้งานเสร็จหรือไม่?
  - **การรั่วไหลของ Event Listener และ Timer (Memory Leak & Cleanup)**: มีการผูก `addEventListener` หรือสร้าง `setInterval` ซ้ำๆ ในลูปหรือตอนเปลี่ยนหน้าจอโดยไม่มีการถอดออก (`removeEventListener`, `clearInterval`) หรือไม่? ซึ่งจะทำให้เกิด Memory Leak และฟังก์ชันทำงานซ้ำซ้อน

### ระดับที่ 2: การไหลของข้อมูลและสถานะ (Data Flow, State Integrity & Cache Sync)
- **ความปลอดภัยเมื่อกดยกเลิก (Cancel vs Save)**: เมื่อผู้ใช้แก้ไขข้อมูลแต่กดยกเลิก ข้อมูลเดิมกลับมาครบ 100% หรือไม่ หรือมีตัวแปรบางตัวแอบเปลี่ยนค่าไปแล้ว?
- **การรั่วไหลของการแก้ไขข้อมูล (Data Mutation / Side Effects)**: ฟังก์ชันมีการแอบไปแก้ไขค่าใน Object หรือ Array ต้นทางโดยตรงหรือไม่?
- **ช่องโหว่การข้ามขั้นตอน (Validation Bypass)**: มีจุดใดที่ผู้ใช้สามารถแก้ไขข้อมูลโดยข้ามขั้นตอนการตรวจสอบหลักได้หรือไม่?
- **ความสอดคล้องของสัญญาระหว่างโมดูล (Contract & Interface Integrity)**: ข้อมูลที่ส่งข้ามฟังก์ชันหรือข้ามไฟล์ มีชนิดข้อมูล โครงสร้าง Object หรือ Schema ตรงตามที่ผู้รับคาดหวังหรือไม่ (เช่น ฟังก์ชันผู้รับคาดหวัง Object แต่ผู้ส่งส่งมาเป็น String หรือ Array)?
- **ความสอดคล้องของแหล่งข้อมูลหลายชุด (Cache & State Desynchronization)**: เมื่อข้อมูลในหน่วยความจำ (RAM) เปลี่ยน มีการอัปเดตหรือล้างค่าในแคช (LocalStorage, Session, DB Cache) หรือไม่? มีโอกาสที่ผู้ใช้รีเฟรชแล้วระบบดึงข้อมูลเก่าที่ค้างในแคชมาแสดงทับหรือไม่?
- **การรั่วไหลของข้อมูลลับและข้อมูลส่วนบุคคล (Sensitive Data Exposure)**: มีการเผลอเขียนคำสั่งพิมพ์ข้อมูลสำคัญ (เช่น Passwords, Tokens, ข้อมูลส่วนบุคคล PII) ออกทาง `console.log`, บันทึก Log, หรือพ่นออกทาง Network Response หรือไม่?
- **การตั้งเวลาหมดอายุของเครือข่าย (Network Timeout & Fallback)**: เมื่อมีการเรียก API ภายนอกหรือดึงข้อมูลผ่านเครือข่าย (เช่น `fetch`, `axios`) มีการตั้งค่า Timeout (`AbortController` หรือ Timeout Signal) หรือไม่? มีแผนสำรอง (Fallback) เมื่อเน็ตหลุดหรือเซิร์ฟเวอร์ไม่ตอบสนองหรือไม่ เพื่อป้องกันไม่ให้ระบบค้างที่สถานะ Loading ตลอดกาล
- **ความปลอดภัยของระบบที่ใช้ AI (AI & Prompt Safety - หากมีการใช้ LLM)**: 
  - มีการนำข้อมูลนำเข้าจากผู้ใช้ (User Input) ไปต่อท้าย Prompt ส่งให้โมเดลโดยตรงโดยไม่ทำความสะอาด (เสี่ยงต่อ Prompt Injection) หรือไม่?
  - มีการควบคุมขนาดข้อความ (Context Window Budget) และกำหนดกรอบการตอบสนอง (Role/Tone/Guardrails) เพื่อไม่ให้โมเดลตอบข้อมูลนอกลู่นอกทางหรือไม่?

### ระดับที่ 3: ความสอดคล้องกับมาตรฐานและการใช้งานจริง (Domain Reality & Operations)
- **ความขัดแย้งกับมาตรฐานของโดเมน**: โค้ดคำนวณตัวเลขได้ แต่ขัดกับวิธีปฏิบัติจริงของธุรกิจหรือระเบียบของหน่วยงานหรือไม่?
- **การส่งออกและนำไปใช้ (Export/Print Reality)**: ข้อมูลที่แสดงบนหน้าจอ เมื่อสั่งพิมพ์ (Print) หรือส่งออกเป็นไฟล์ (PDF, Excel, JSON) ข้อมูลครบถ้วนและจัดหน้าถูกต้องหรือไม่?

## 4. การตรวจสอบส่วนต่อประสานและความเป็นมิตรต่อผู้ใช้ (Interface & User-Friendliness)

แยกเกณฑ์การตรวจตามประเภทของโปรแกรม:

### กรณีที่ 4.1: โปรแกรมที่มีหน้าจอ (GUI: Web / Mobile / Desktop App)
1. **การแจ้งสถานะของระบบ (Loading States)**: มีตัวหมุน (Spinner) หรือข้อความบอกหรือไม่เมื่อระบบกำลังทำงาน เพื่อไม่ให้ผู้ใช้นึกว่าโปรแกรมค้าง
2. **ความเข้าใจง่ายของข้อความเตือน (Error Message Clarity)**: ไม่แสดงรหัสเทคนิคที่คนอ่านไม่เข้าใจ (เช่น `Error 500`, `[object Object]`) แต่ต้องบอกว่าเกิดอะไรขึ้นและต้องแก้ไขอย่างไร
3. **การป้องกันข้อผิดพลาดและการให้อภัย (Error Prevention & Undo)**: การลบข้อมูลสำคัญต้องมีกล่องถามยืนยันเสมอ มีปุ่มกดยกเลิกที่ทำงานได้จริง
4. **ลำดับสายตาและความสำคัญของปุ่ม (Visual Hierarchy)**: ปุ่มหลักกับปุ่มรองแยกสีชัดเจน ปุ่มอันตราย (เช่น ลบ) ไม่วางติดกับปุ่มบันทึกจนเสี่ยงกดผิด
5. **การรองรับหน้าจอและการอ่านง่าย (Responsive Layout)**: บนจอขนาดเล็กตัวหนังสือไม่เล็กเกินไป ตารางไม่ล้นจอ และสีตัวหนังสืออ่านสบายตา
6. **การแจ้งสถานะเมื่อสำเร็จ (Success Feedback)**: เมื่อผู้ใช้ทำงานสำคัญสำเร็จ (เช่น บันทึกข้อมูล, ส่งออกไฟล์) มีข้อความแจ้งเตือนที่ชัดเจน (เช่น Toast Notification หรือ Modal ยืนยัน) หรือไม่ เพื่อป้องกันไม่ให้ผู้ใช้สับสนและกดปุ่มซ้ำ
7. **การลดภาระทางสมอง (Cognitive Load & Information Density)**: หน้าจอไม่ยัดเยียดข้อความหรือตัวเลือกมากเกินไป มีการจัดกลุ่มข้อมูลเป็นหมวดหมู่ (เช่น Tabs, Accordion, หรือ Steps) เพื่อไม่ให้ผู้ใช้เกิดความสับสนหรือตาล้า

### กรณีที่ 4.2: โปรแกรมที่ไม่มีหน้าจอ (Headless: Backend API / CLI / Script)
1. **ความชัดเจนของคำสั่งและความช่วยเหลือ (CLI Help & Usage Guidance)**: มีคำสั่ง `--help` อธิบายวิธีใช้และพารามิเตอร์ที่ถูกต้องชัดเจนหรือไม่
2. **รูปแบบข้อความตอบกลับข้อผิดพลาด (Structured Error Responses)**: 
   - สำหรับ API: ส่งรหัสสถานะ HTTP ที่ถูกต้อง (เช่น 400 สำหรับข้อมูลผิด, 404 สำหรับหาไม่พบ) พร้อม JSON ที่มีฟิลด์ `message` อธิบายสาเหตุชัดเจน
   - สำหรับ CLI: ส่งออกข้อความแจ้งเตือนทาง `stderr` และมี Exit Code ที่ไม่ใช่ 0 เมื่อเกิดข้อผิดพลาด
3. **การแสดงความคืบหน้าของงานระยะยาว (Progress Indicators)**: หากสคริปต์ต้องใช้เวลาประมวลผลนาน มี Progress Bar หรือพิมพ์ Log บอกความคืบหน้าหรือไม่ เพื่อไม่ให้ผู้ใช้นึกว่าสคริปต์ค้าง

## 5. โหมดเจาะลึก: ความทนทานต่อการใช้งานจริง (Deep Mode: Runtime Resilience)

> **ข้อกำหนดการตรวจ**: ให้เลือกตรวจโหมดเจาะลึกเฉพาะ **จุดเสี่ยงวิกฤต (Critical Paths) สูงสุด 1–3 จุดต่อการตรวจ 1 ครั้ง** เพื่อป้องกันข้อความยาวเกินขีดจำกัด โดยใช้เกณฑ์คัดเลือกจุดวิกฤตดังนี้:
> 1. ฟังก์ชันจัดการสิทธิ์ ยืนยันตัวตน หรือเซสชัน (Authentication / Authorization / Session)
> 2. ฟังก์ชันคำนวณเงิน คะแนน เกรด หรือตัวเลขสำคัญทางธุรกิจ
> 3. ฟังก์ชันบันทึก อัปเดต หรือลบข้อมูลหลัก (Core State Mutation & Database/Storage Write)
> 4. ฟังก์ชันที่มีการส่งข้อมูลข้ามเครือข่ายหรือเชื่อมต่อ API ภายนอก (Network I/O & External APIs)

1. **การกดย้ำๆ และการส่งคำขอซ้ำรัวๆ (Rapid Triggers & Concurrency)**:
   - หากกดยืนยันซ้ำๆ 2–3 ครั้งติดกัน ระบบส่งคำขอซ้ำซ้อนหรือไม่? มีการล็อกปุ่ม (Disable) ทันทีที่กดหรือไม่? มีการยกเลิกคำขอเดิมที่ค้างอยู่หรือไม่?
2. **การแอบเปลี่ยนข้อมูลในหน่วยความจำ (Unsaved State Leaks)**:
   - เมื่อเปิดหน้าแก้ไขแล้วพิมพ์ค่าใหม่ แต่ยังไม่กดบันทึก หากเปลี่ยนหน้าจอหรือกดยกเลิก ข้อมูลที่พิมพ์ค้างไว้หลุดไปแสดงที่อื่นหรือไม่?
3. **การกู้คืนเมื่อข้อมูลเสียหาย (Corrupted Data Recovery)**:
   - หากปิดโปรแกรมหรือเน็ตหลุดระหว่างกำลังบันทึกข้อมูล ทำให้ไฟล์หรือ LocalStorage มีข้อมูลแค่ครึ่งเดียว เมื่อเปิดใหม่ โปรแกรมจะหน้าขาว/แคลช (Crash) ทันที หรือมีระบบดึงค่าเริ่มต้นมาใช้แทน?
4. **อักขระพิเศษและการทำลายรูปแบบ (Special Characters & Formatting Injection)**:
   - หากผู้ใช้พิมพ์เครื่องหมายคำพูด (`"`, `'`), วงเล็บ (`<`, `>`), หรือขีด (`\`, `/`) หน้าจอแสดงผลเพี้ยน ตารางแตก หรือทำให้ระบบอ่านข้อมูลไม่ได้หรือไม่?

## 6. การจำลองสถานการณ์ความผิดพลาดและระดับความรุนแรง

### เกณฑ์การจำลองสถานการณ์ (Counter-Example Protocol):
- **ระดับ Critical และ Moderate**: ต้องระบุ 3 ส่วนเสมอ:
  1. **Trigger Scenario (Input หรือลำดับเหตุการณ์)**: ข้อมูลนำเข้า หรือ **ลำดับจังหวะเวลาของเหตุการณ์** (เช่น เหตุการณ์ A เกิดขึ้นก่อนที่เหตุการณ์ B จะบันทึกเสร็จ) ที่ทำให้ระบบพัง
  2. **ผลลัพธ์จริงที่โค้ดทำ (Actual Output)**: พฤติกรรมหรือข้อผิดพลาดที่เกิดขึ้นจริง
  3. **ผลลัพธ์ที่ถูกต้อง (Expected Output)**: สิ่งที่ควรจะเป็นตามมาตรฐาน
- **ระดับ Minor**: สรุปเป็นตาราง 1 บรรทัด (ตำแหน่งโค้ด | ปัญหา | วิธีแก้) เพื่อประหยัดพื้นที่ข้อความ

### เกณฑ์การแยกแยะระดับความรุนแรง (Severity Rating):
* **Critical (ระดับสูง)**: 
  - ข้อมูลสูญหาย, ระบบค้าง/แคลช, คำนวณตรรกะหลักผิดพลาด, เกิดลูปไม่รู้จบ/หน่วยความจำหมด (OOM)
  - **ความปลอดภัยและการละเมิดสิทธิ์**: การข้ามระบบตรวจสอบสิทธิ์ (Authorization / Access Control Bypass / IDOR), ผู้ใช้ทั่วไปเข้าถึงข้อมูลหรือคำสั่งของแอดมินได้, หรือ UI ไม่มีปุ่มยืนยันก่อนลบข้อมูลสำคัญ
* **Moderate (ระดับกลาง)**: 
  - ตรรกะผิดเฉพาะบางกรณี (Edge Cases), แคชไม่ตรงกับข้อมูลจริง (Cache Desync), ความไม่สอดคล้องของสัญญาระหว่างโมดูล (Contract Mismatch)
  - **ด้าน UI/UX**: สิ่งที่ **ขัดขวางการทำงานของผู้ใช้ หรือทำให้เข้าใจสถานะระบบผิด** เช่น ไม่มีตัวหมุนบอกสถานะจนนึกว่าโปรแกรมค้าง, ข้อความเตือนเป็นภาษาเทคนิคที่ไม่บอกวิธีแก้ไข, หรือไม่มีระบบป้องกันการกดปุ่มซ้ำ
* **Minor (ระดับต่ำ)**: 
  - สิ่งที่ระบบยังทำงานได้สมบูรณ์ ผู้ใช้เข้าใจได้ แต่ **ดูไม่สวยงามหรือไม่สะดวกสบาย** เช่น ตารางล้นหน้าจอเล็กน้อย, สีปุ่มไม่เด่นชัด, หรือการเว้นวรรคไม่เรียบร้อย

> **กฎการตัดสินเมื่อความรุนแรงก้ำกึ่ง (Tie-Breaking Rule)**: หากข้อผิดพลาดใดก้ำกึ่งระหว่าง Critical และ Moderate แต่เกี่ยวข้องกับ **ความปลอดภัยของระบบ, สิทธิ์การเข้าถึง, หรือการสูญหายของข้อมูล** ให้ตัดสินปัดขึ้นเป็นระดับ **Critical** เสมอ

## 7. รูปแบบการรายงานผล (Audit Report Format)

```markdown
### ข้อมูลการตรวจสอบ
* **โมดูล/ไฟล์ที่ตรวจ**: `...`
* **ประเภทโปรแกรม**: [GUI Web / Mobile / Desktop / Headless API / CLI / Script]
* **โดเมนความรู้ที่เกี่ยวข้อง**: `...` (มาตรฐานทางการ หรือ ตรรกะเฉพาะตัวของระบบ)
* **ผลการรัน Pre-Check (Linter/Tests)**: [PASS (0 errors) / FAIL (สรุปสั้นๆ) / ไม่พบชุดทดสอบอัตโนมัติในโปรเจกต์]

---

### ตารางสรุปผลการตรวจสอบ (Executive Summary)

| ระดับความรุนแรง | ตำแหน่งที่พบ | จุดผิดพลาด / ที่ขาดไป | ผลกระทบที่เกิดขึ้นจริง | แนวทางแก้ไข |
|---|---|---|---|---|
| `Critical/Moderate/Minor` | `ไฟล์:บรรทัด` | สรุปสั้นๆ | สรุปสั้นๆ | สรุปสั้นๆ |

---

### [ระดับความรุนแรง: Critical/Moderate] หัวข้อปัญหา (ระบุไฟล์และบรรทัดโค้ด)

* **ตำแหน่งโค้ด**: `ไฟล์:บรรทัด`
* **สมมติฐานที่ผิดพลาด**: โค้ดส่วนนี้สมมติอะไรไว้ แต่ความจริงไม่เป็นเช่นนั้น
* **การจำลองสถานการณ์ (Counter-Example)**:
  - Input หรือลำดับเหตุการณ์: ...
  - ผลลัพธ์ที่โค้ดทำ: ...
  - สิ่งที่ควรจะเป็น: ...
* **ผลกระทบต่อการใช้งานจริง**: เกิดอะไรขึ้นกับระบบหรือผู้ใช้งาน (เช่น ผู้ใช้สับสน, ข้อมูลหาย, CPU พุ่ง 100%)
* **แนวทางแก้ไขขั้นต่ำ (Minimal Fix)**: วิธีแก้ที่ตรงจุด กระทบโค้ดส่วนอื่นน้อยที่สุด โดย **ต้องแก้ที่ต้นตอจริงของปัญหา (Root Cause)** ห้ามเสนอวิธีแก้แบบปะผุอาการเฉพาะหน้า (Symptom Patching เช่น การใส่ if ดัก null ลอยๆ โดยไม่แก้จุดที่สร้าง null ขึ้นมา) พร้อมระบุจุดที่ต้องระวังผลกระทบข้างเคียง
* **วิธีตรวจสอบผล (Verification Method)**: ระบุคำสั่งเทส (Automated Test) หรือขั้นตอนการตรวจสอบด้วยตนเอง (Manual Step) สั้นๆ เพื่อยืนยันว่าแก้ปัญหาสำเร็จจริง

---

### รายการข้อบกพร่องระดับต่ำ (Minor Issues)
| ตำแหน่งที่พบ | ปัญหาที่พบ | แนวทางแก้ไข |
|---|---|---|
| `ไฟล์:บรรทัด` | รายละเอียดสั้นๆ | วิธีแก้สั้นๆ |
```
